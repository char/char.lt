okay. you know already know what [`jj`](https://jj-vcs.dev/) (jujutsu for long) is, right? like, vaguely? it's like a `git` but it's compatible with `git` and your most annoying oomfs all love it and you always _say_ you've been meaning to give it a try some day but like you aren't really pressed because git is like, good enough..? that one. let me teach you how to become one of those annoying oomfs. you're gonna love it.

## getting started

step one is you install jj. i literally get it from `nixpkgs` and `winget` which covers linux mac and windows; jj is probably in _your_ system's[^1] package manager as well.

step two is you use jj. i will teach you how to use jj in just a second.

[^1]: [_my_ system?](https://www.shutterstock.com/image-photo/irresolute-young-man-pointing-finger-himself-158016434)

## the jj mental model

at a super high level, as a git-compatible version control system, jj tracks a bunch of commits. in jj, each commit is part of a 'revision' which has a stable **change ID**, _separate_ to its commit ID: jj gives each commit a "visible" flag, and gives you the illusion of few mutable revisions by creating many immutable commits under the same change IDs, marking the present version hidden and the new version visible, while automatically rebasing child and descendant commits to the new version.

that's pretty abstract, so let's take a look at how jj presents revisions to us:

<pre class="terminal"><code><a-13>watch-party/</a-13> (jj: rsku) $ <a-2>jj</a-2> log
<a-2 b>@</a-2>  <a-13 b>r</a-13><a-8 b>skulwum</a-8> <a-3 b>charlotte@som.codes</a-3> <a-14 b>2026-05-13 00:32:36</a-14> <a-12 b>0</a-12><a-8 b>01afa51</a-8>
│  <a-10 b>(empty) (no description set)</a-10>
<a-14 b>◆</a-14>  <a-5 b>m</a-5><a-8>xklzpnz</a-8> <a-3>charlotte@som.codes</a-3> <a-6>2026-05-12 14:02:50</a-6> <a-5>main</a-5> <a-4 b>fb4</a-4><a-8>5c965</a-8>
│  tweak the sounds a little
<a-14 b>◆</a-14>  <a-5 b>ll</a-5><a-8>oylxvy</a-8> <a-3>charlotte@som.codes</a-3> <a-6>2026-05-12 10:33:29</a-6> <a-4 b>81</a-4><a-8>ed6047</a-8>
│  add deno task for formatting and run it
<a-14 b>◆</a-14>  <a-5 b>zn</a-5><a-8>lzuqxr</a-8> <a-3>charlotte@som.codes</a-3> <a-6>2026-05-12 10:33:29</a-6> <a-4 b>e0</a-4><a-8>d55474</a-8>
│  add readycheck command with notification sounds
~
</code></pre>

you can see both IDs in action here - each revision has a _change ID_ in jj's "reverse-hex notation" (it uses the last 16 letters of the alphabet!) as well as a disambiguating commit ID in regular hex notation (1:1 with `git`) to distinguish two commits with the same change ID (e.g. different iterations of the same revision).

the other thing you can note is the green `@` indicating that we're currently checked out on an empty descriptionless commit - this is the _working-copy commit_: instead of having a staging area that you `git add` files to, jj automatically tracks all workdir changes whenever it's invoked and makes you "edit" a commit. this is both simpler and more powerful[^2]: jj unifies the experience of editing a brand new commit and editing any historical or parallel revision, which makes working with branching history or rewriting past history easy. at any time, you can run `jj edit <rev>` to move your workdir to a specific revision, and then directly make your changes on the working copy.

[^2]: [i prefer jj. it is both simpler and more powerful than git](https://bsky.app/profile/jaffray.bsky.social/post/3mpodop7me22c)

## baby's first commit

now that we've built a mental model of jj (malleable _revisions_ made of immutable _commits_, plus a _working-copy commit_), let's get more concrete.

you can type `jj git init` in an empty directory to create a new git-backed jj repo (à la `git init`), _or_ in an existing `git` repository to convert it to a git-backed jj repo. by default, these repos have _git colocation_, which means you can use both `git` commands and `jj` commands to operate on them.

to begin, we'll set our user.name and user.email, just like git:

<pre class="terminal"><code>$ <a-2>jj</a-2> config set <a-6>--user</a-6> user.name <a-3>"My Name"</a-3>
$ <a-2>jj</a-2> config set <a-6>--user</a-6> user.email <a-3>"me@my-site.com"</a-3>
</code></pre>

we first create an empty repository, and see we're on an empty working-copy commit:

<pre class="terminal"><code>$ <a-2>mkdir</a-2> hello-jj &amp;&amp; <a-2>cd</a-2> hello-jj/
<a-13>hello-jj/</a-13> $ <a-2>jj</a-2> git init
<a-13>hello-jj/</a-13> (jj: rkxs) $ <a-2>jj</a-2> log
<a-2 b>@</a-2>  <a-13 b>r</a-13><a-8 b>kxsqzky</a-8> <a-3 b>charlotte@som.codes</a-3> <a-14 b>2026-07-13 10:57:55</a-14> <a-12 b>2</a-12><a-8 b>f832520</a-8>
│  <a-10 b>(empty) (no description set)</a-10>
<a-14 b>◆</a-14>  <a-5 b>z</a-5><a-8>zzzzzzz</a-8> <a-2>root()</a-2> <a-4 b>0</a-4><a-8>0000000</a-8>
</code></pre>

then we can write a conversation to a file, and take a look again. that second line will also give jj a stable diff anchor when we edit history in a couple steps.

<pre class="terminal"><code><a-13>hello-jj/</a-13> (jj: rkxs) $ <a-2>echo</a-2> <a-3>'A: meow!'</a-3> &gt; <a-5>conversation.txt</a-5>
<a-13>hello-jj/</a-13> (jj: rkxs) $ <a-2>echo</a-2> <a-3>'B: what?'</a-3> &gt;&gt; <a-5>conversation.txt</a-5>
<a-13>hello-jj/</a-13> (jj: rkxs) $ <a-2>jj</a-2> log
<a-2 b>@</a-2>  <a-13 b>r</a-13><a-8 b>kxsqzky</a-8> <a-3 b>charlotte@som.codes</a-3> <a-14 b>2026-07-13 10:58:01</a-14> <a-12 b>1</a-12><a-8 b>e8c2f8b</a-8>
│  <a-3 b>(no description set)</a-3>
<a-14 b>◆</a-14>  <a-5 b>z</a-5><a-8>zzzzzzz</a-8> <a-2>root()</a-2> <a-4 b>0</a-4><a-8>0000000</a-8>
</code></pre>

you can see our commit ID has changed from `2f83` to `1e8c`, but our revision is still `rkxs`. let's give this commit a description:

<pre class="terminal"><code><a-13>hello-jj/</a-13> (jj: rkxs) $ <a-2>jj</a-2> describe <a-6>-m</a-6> <a-3>"say meow"</a-3>
Working copy  (@) now at: <a-13 b>r</a-13><a-8 b>kxsqzky</a-8> <a-12 b>8</a-12><a-8 b>ee550a9</a-8> <a-b>say meow</a-b>
Parent commit (@-)      : <a-5 b>z</a-5><a-8>zzzzzzz</a-8> <a-4 b>0</a-4><a-8>0000000</a-8> <a-2>(empty)</a-2> <a-2>(no description set)</a-2>
<a-13>hello-jj/</a-13> (jj: rkxs) $ <a-2>jj</a-2> log
<a-2 b>@</a-2>  <a-13 b>r</a-13><a-8 b>kxsqzky</a-8> <a-3 b>charlotte@som.codes</a-3> <a-14 b>2026-07-13 10:58:06</a-14> <a-12 b>8</a-12><a-8 b>ee550a9</a-8>
│  <a-b>say meow</a-b>
<a-14 b>◆</a-14>  <a-5 b>z</a-5><a-8>zzzzzzz</a-8> <a-2>root()</a-2> <a-4 b>0</a-4><a-8>0000000</a-8>
</code></pre>

## baby's second commit

now we can work on top of this revision. let's add some more content to `conversation.txt`:

<pre class="terminal"><code><a-13>hello-jj/</a-13> (jj: rkxs) $ <a-2>jj</a-2> new
Working copy  (@) now at: <a-13 b>z</a-13><a-8 b>tklkwuv</a-8> <a-12 b>6</a-12><a-8 b>7bf7c3a</a-8> <a-10 b>(empty) (no description set)</a-10>
Parent commit (@-)      : <a-5 b>r</a-5><a-8>kxsqzky</a-8> <a-4 b>8</a-4><a-8>ee550a9</a-8> say meow
<a-13>hello-jj/</a-13> (jj: ztkl) $ <a-2>echo</a-2> <a-3>'A: i mean, hello.'</a-3> &gt;&gt; <a-5>conversation.txt</a-5>

B: what?
A: i mean, hello.
<a-13>hello-jj/</a-13> (jj: ztkl) $ <a-2>jj</a-2> describe <a-6>-m</a-6> <a-3>"say hello as well"</a-3>
<a-dim>[…]</a-dim>
<a-13>hello-jj/</a-13> (jj: ztkl) $ <a-2>jj</a-2> log
<a-2 b>@</a-2>  <a-13 b>z</a-13><a-8 b>tklkwuv</a-8> <a-3 b>charlotte@som.codes</a-3> <a-14 b>2026-07-13 11:21:01</a-14> <a-12 b>6</a-12><a-8 b>5f77d30</a-8>

the real power of jj isn't the usual 'append commit' workflow though, it's in the ease of history editing.

## baby's second first commit

let's go back and change the meow commit to say 'woof' instead!

<pre class="terminal"><code><a-13>hello-jj/</a-13> (jj: ztkl) $ <a-2>jj</a-2> edit rk
<a-dim>[…]</a-dim>
<a-13>hello-jj/</a-13> (jj: rkxs) $ <a-2>echo</a-2> <a-3>'A: woof!'</a-3> &gt; <a-5>conversation.txt</a-5>
<a-13>hello-jj/</a-13> (jj: rkxs) $ <a-2>echo</a-2> <a-3>'B: what?'</a-3> &gt;&gt; <a-5>conversation.txt</a-5>
<a-13>hello-jj/</a-13> (jj: rkxs) $ <a-2>jj</a-2> edit zt
<a-dim>[…]</a-dim>
<a-13>hello-jj/</a-13> (jj: ztkl) $ <a-2>cat</a-2> <a-5>conversation.txt</a-5>
A: woof!
B: what?
A: i mean, hello.
</code></pre>

the change with id `ztklkwuv` was automatically rebased onto our new version of `rkxsqzky`, and the files reflect the synthesis of both commits.

<pre class="terminal"><code><a-13>hello-jj/</a-13> (jj: ztkl) $ <a-2>jj</a-2> log
<a-2 b>@</a-2>  <a-13 b>z</a-13><a-8 b>tklkwuv</a-8> <a-3 b>charlotte@som.codes</a-3> <a-14 b>2026-07-13 11:45:26</a-14> <a-12 b>3</a-12><a-8 b>4f3de32</a-8>
│  <a-b>say hello as well</a-b>
○  <a-5 b>r</a-5><a-8>kxsqzky</a-8> <a-3>charlotte@som.codes</a-3> <a-6>2026-07-13 11:44:21</a-6> <a-4 b>3</a-4><a-8>4af2929</a-8>
│  say meow
<a-14 b>◆</a-14>  <a-5 b>z</a-5><a-8>zzzzzzz</a-8> <a-2>root()</a-2> <a-4 b>0</a-4><a-8>0000000</a-8>
</code></pre>

and we can easily reword the commit as well:

<pre class="terminal"><code><a-13>hello-jj/</a-13> (jj: ztkl) $ <a-2>jj</a-2> describe <a-6>-r</a-6> rk <a-6>-m</a-6> <a-3>"say woof"</a-3>
Rebased 1 descendant commits
Working copy  (@) now at: <a-13 b>z</a-13><a-8 b>tklkwuv</a-8> <a-12 b>2</a-12><a-8 b>a2e7291</a-8> <a-b>say hello as well</a-b>
Parent commit (@-)      : <a-5 b>r</a-5><a-8>kxsqzky</a-8> <a-4 b>2</a-4><a-8>65ff44e</a-8> say woof
</code></pre>

as with git, you can also run `jj describe` without a `-m` flag, which will open an editor for you to write a full commit description (i use helix, personally) - you can configure which editor is used via `jj config set --user ui.editor <editor>`, which will edit `~/.config/jj/config.toml`.

## working with remotes

so that's all good, but how do we push and pull to a jj remote? we haven't talked about branches at all!

in jj, the analog to git's _branch_ model is _bookmarks_. bookmarks work anywhere jj expects a _revset_ (e.g. a change ID or commit ID) to identify a commit, so `jj describe -r main` is a valid command, for example.

anyway, let's say you want to push up to a git remote at `my-server.com`. we add our remote via `git` as usual (remember we have colocation!), `set` a bookmark to create a new one, and then `track` it to the pertinent remote. after all that, we can push:

<pre class="terminal"><code><a-13>hello-jj/</a-13> (jj: ztkl) $ <a-2>git</a-2> <a-3>remote</a-3> <a-3>add</a-3> <a-12>origin</a-12> <a-12>'git@my-server.com:hello-jj.git'</a-12>
<a-13>hello-jj/</a-13> (jj: ztkl) $ <a-2>jj</a-2> bookmark set main
Created 1 bookmarks pointing to <a-13 b>z</a-13><a-8 b>tklkwuv</a-8> <a-12 b>2</a-12><a-8 b>a2e7291</a-8> <a-13 b>main</a-13><a-8 b> | </a-8><a-b>say hello as well</a-b>
<a-13>hello-jj/</a-13> (jj: ztkl) $ <a-2>jj</a-2> bookmark track main <a-6>--remote=origin</a-6>
Started tracking 1 remote bookmarks.
<a-13>hello-jj/</a-13> (jj: ztkl) $ <a-2>jj</a-2> git push
Changes to push to origin:
  bookmark: main [add to 2a2e7291]
<a-dim>[…]</a-dim>
</code></pre>

there's no `pull`, but when there are remote changes you want to incorporate you can `jj git fetch` and `jj new [bookmark]` to create a new revision 'on top' of the bookmark and switch to it as the working copy.

<pre class="terminal"><code><a-13>hello-jj/</a-13> (jj: ztkl) $ <a-2>jj</a-2> git fetch
<a-dim>[…]</a-dim>
bookmark: <a-5>main@origin</a-5> [updated] tracked
<a-13>hello-jj/</a-13> (jj: ztkl) $ <a-2>jj</a-2> new main
Working copy  (@) now at: <a-13 b>x</a-13><a-8 b>wzkpmyw</a-8> <a-12 b>c</a-12><a-8 b>807550a</a-8> <a-10 b>(empty) (no description set)</a-10>
Parent commit (@-)      : <a-5 b>o</a-5><a-8>vxwxtzx</a-8> <a-4 b>d</a-4><a-8>3be7058</a-8> <a-5>main</a-5><a-8> | </a-8>add another greeting
Added 0 files, modified 1 files, removed 0 files
<a-13>hello-jj/</a-13> (jj: xwzk) $ <a-2>cat</a-2> <a-5>conversation.txt</a-5>
A: woof!
B: what?
A: i mean, hello.
C: hi guys
</code></pre>

## next steps

the main goal of this primer is to be a shortcut that makes other material more approachable for you, but there's a lot of ground i've left uncovered! for instance, you will probably want to get comfortable with `jj squash` / `jj rebase` / `jj arrange` for actual history-gardening, but these are well-covered by others' writings on jj.
